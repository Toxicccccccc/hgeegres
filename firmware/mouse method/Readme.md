This started as a research question: can we build a forward-generative movement model grounded in actual motor control science that produces trajectories indistinguishable from real human input under statistical analysis? Turns out, yes. Let me walk you through it.


The Problem With WindMouse

WindMouse has been the go-to for over a decade. It's simple, it's fast, and at a glance the paths look human. But it has fundamental problems that show up the moment you run any real analysis on its output:
No Fitts' Law compliance - movement time has no relationship to task difficulty
No biomechanical basis - "gravity" and "wind" are heuristic forces, not motor control primitives
Velocity profile is jagged, not bell-shaped - the wind force creates constant oscillations
Sub-movement count is absurd (10-20+ peaks) - real humans produce 1-3
Timing is uniform random - real inter-sample intervals follow a gamma distribution
No tremor model, no signal-dependent noise, no direction-dependent curvature

Any classifier looking at angular distributions, velocity zero-crossings, or acceleration reversals will flag WindMouse output in a heartbeat. The spatial path might fool your eyes, but the temporal dynamics are a dead giveaway.


What SigmaDrift Does Differently

SigmaDrift is a hybrid biomechanical-stochastic model that combines six components from computational motor control research into a single forward-generative algorithm. Every component has a basis in published neuroscience:

The key insight is that none of these are bolted on independently. They interact: signal-dependent noise makes Fitts' Law emerge naturally from the model, tremor suppression during the ballistic phase means noise characteristics change with movement phase, and the OU drift creates organic wandering that a constant-frequency jitter never could.


Algorithm Architecture

The movement is generated in three stages:

1. Planning

Given start point, target point, and target width, the algorithm computes:
- Movement time from Fitts' Law (Shannon formulation) with lognormal jitter
- Primary ballistic stroke distance (92-97% of total, or 102-108% for overshoot)
- 0-2 corrective sub-movements for the remaining distance
- Direction-dependent curvature amplitude

Code:
MT = (a + b * log2(D/W + 1)) * exp(N(0, 0.08))
 
Primary reach factor:
  85% chance: uniform(0.92, 0.97)  // undershoot
  15% chance: uniform(1.02, 1.08)  // overshoot
That 15% overshoot probability matches empirical data from Müller et al. (2017) on human pointing.

2. Velocity Profile Generation

Each sub-movement's timing follows a sigma-lognormal velocity primitive. The critical detail: we use the analytical CDF of the lognormal distribution to compute path progress, which means zero numerical integration.

Code:
progress(t) = Φ((ln(t - t0) - μ) / σ)
 
where μ = ln(peak_time) + σ²
      peak_time ≈ 35% of MT
The μ derivation comes from the lognormal mode: mode = exp(μ - σ²). We want peak velocity at ~35% of movement time, so we solve for μ. This produces the characteristic asymmetric bell-shaped velocity profile: fast rise, slow tail. The exact shape that BeCAPTCHA-Mouse's 37-dimensional feature extractor looks for.

3. Noise Composition

Three noise sources are applied at each timestep:

Code:
// ornstein-uhlenbeck lateral drift (euler-maruyama discretization)
ou += -θ * ou * dt + σ_ou * √dt * N(0,1)
 
// physiological tremor with proprioceptive suppression
tremor = amplitude * (1 / (1 + speed * 0.3)) * sin(2π * freq * t + phase)
 
// harris-wolpert signal-dependent noise
sdn = k * speed * N(0,1)
The tremor suppression is the detail that matters. During the fast ballistic phase, tremor gain drops because proprioceptive feedback dampens it. During the slow corrective phase and at rest, tremor is fully expressed. This is exactly how the human motor system works, and it's a feature no other movement algorithm implements.


Direction-Dependent Curvature

Human movements in different directions have different curvature profiles because of wrist/forearm biomechanics. Horizontal movements (primarily wrist rotation) are straighter than vertical movements (primarily forearm flexion/extension).

SigmaDrift models this with a perpendicular offset along the path:

Code:
curvature_amplitude = distance * 0.025 * direction_factor(angle) * N(0, 1)
 
direction_factor(angle):
  horizontal: ~0.35 (minimal curvature)
  diagonal:   ~0.75
  vertical:   ~1.15 (maximum curvature)
 
Offset profile: s²(1-s)³ normalized, peaks at s=0.4
  (curvature is maximal during the acceleration phase, not the midpoint)
The asymmetric curvature profile peaking at 40% of the path is based on the observation that trajectory deviation is greatest during the acceleration phase when the motor command is largest. Not at the midpoint like a Bezier curve would give you.

Config Parameters That Matter

Most of the defaults are good, but here's what you'd want to tune if you wanted to make something to bypass detection or have a stronger feeling:

Code:
/* Chart generated by Claude */
 
Parameter           | Default | Effect
--------------------|---------|-----------------------------------------------
fitts_a / fitts_b   | 50/150  | Movement time scaling. Calibrate to your target app.
target_width        | 20.0    | Wider = faster movement, narrower = slower + more corrections
overshoot_prob      | 0.15    | 15% of movements overshoot. Raise for "nervous" behavior.
curvature_scale     | 0.025   | Path curvature amount. 0 = straight lines.
ou_sigma            | 1.2     | Lateral drift intensity. Higher = more visible wobble.
tremor_amp_max      | 0.55    | Hand tremor ceiling. Raise for less steady hands.
sdn_k               | 0.04    | Signal-dependent noise. Higher = more jitter during fast moves.
sample_dt_mean      | 7.8     | Mean polling interval (ms). 7.8 ≈ 128Hz.
The most impactful parameter is target_width. Smaller targets produce longer, more careful movements with more corrections, exactly like a real human. If you're clicking small UI elements, set this to match the element size.


What Makes This Actually Novel/Why Would You Use This

There are existing algorithms that use individual components (minimum-[removed] paths, lognormal timing, OU noise). SigmaDrift's contribution is the composition:
Forward-generative sigma-lognormal - Previous work (BeCAPTCHA-Mouse) uses sigma-lognormal decomposition to DETECT bots by analyzing existing trajectories. SigmaDrift flips this: we GENERATE trajectories from sigma-lognormal primitives with biomechanically-derived parameters. If the detector's feature space is sigma-lognormal, and you're generating in that same space, you're already speaking the right language.
Analytical CDF progression - No numerical integration, no Euler stepping along the path. Progress along the curve is computed directly from the lognormal CDF (which reduces to erf). This makes the algorithm O(N) with minimal per-sample cost.
Multiplicative signal-dependent noise - This is the Harris-Wolpert principle: motor noise scales with the magnitude of the motor command. This single property is what can cause Fitts' Law to emerge from the model naturally rather than being hardcoded, but unfortunately for this version it is prescribed. Larger movements require larger commands, which produce more noise, which reduces accuracy, which requires more correction time.
Speed-modulated tremor - No other movement algorithm models the proprioceptive suppression of tremor during fast movement. It's a small detail, but it means the noise characteristics change between the ballistic and corrective phases, exactly like real motor output.


Limitations

Of course, I have to be honest about what this doesn't do:
No learned component - this is a parametric model, not a neural network. It won't adapt to a specific user's movement style without manual parameter tuning. A GAN or diffusion model fitted to recorded data would be more personalized.
Single-segment only - generates point-to-point movements. Chaining multiple segments (e.g. menu navigation) requires calling generate() multiple times with appropriate pauses between.
No fatigue modeling - movement characteristics change over long sessions. This doesn't model that.
Fitts' Law constants (a, b) are hardcoded defaults - for best results, calibrate these to the application context.
